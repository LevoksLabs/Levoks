# Full-stack contracts and executable integrations

## Multiple Select selection limits

Select controls with Multiple enabled now use the same Minimum/Maximum selections editor as Checkbox Group. Bounds are whole numbers from 0 to 200: blank minimum means zero, blank maximum permits all enabled choices, and Required raises the effective minimum to one. Explicit Apply rejects invalid bounds and excess selected defaults before a history change. Defaults may be below the minimum while authoring. Disabling or removing choices still clears their defaults. Guided collection creation and mapped compilation require enough enabled choices, including native option-group disabling.

Visible count instructions are associated with the native select and retain authored helper text. A positive minimum sets native Required; preview/export count enabled options before transport, announce under/over selection, focus the select and preserve the user's entries. Disabled controls and inactive conditional sections are omitted. Optional empty multiple selects retain their existing empty-array serialization; maximum zero allows an empty array or omission. Single-select mode ignores retained bounds, and switching back restores them. Both select definitions support saved scalar and multiple defaults without unknown-property import failures.

New guided collections snapshot strict editable `minItems`/`maxItems` rules into ordinary backend validation alongside Allowed values. Positive minima reject missing arrays; maxima permit omission. Conditional counts execute only in the active branch and their endpoint/model fields remain optional. Existing backend rules do not migrate after visual edits: review them explicitly. Reproduce local authoring, download and production Next/Express/MongoDB acceptance with `npm run test:select-metadata-export`. Compound/select-driven conditions, mixed/nested composites and broader accessibility acceptance remain incomplete.

## Checkbox selection limits

Checkbox Group Content has Minimum selections and Maximum selections drafts with an atomic Apply. Bounds are whole numbers from 0 to 200; blank minimum means zero and blank maximum allows all enabled choices. Required raises the effective minimum to one. Minimum above maximum, invalid numbers and too many selected defaults fail without changing the document. Limits follow undo/redo, save/reload, copies and reusable definitions. Existing projects without these properties retain their previous behavior. Draft groups may have fewer choices while being built; guided storage and connected export require enough enabled choices to meet the effective minimum.

Canvas, preview and export share visible selection instructions associated with the native fieldset. Generated submission checks count enabled, checked choices owned by the form, preserve entries on failure, announce the error in the form status and focus an enabled checkbox for keyboard recovery. Hidden or disabled groups remain omitted. A positive minimum requires a selection even when Required is unchecked. Optional empty groups remain omitted; zero maximum permits omission only.

New guided storage snapshots limits into ordinary editable Minimum selections (`minItems`) and Maximum selections (`maxItems`) Validation rules, alongside Allowed values. Rules require actual arrays, never coerce strings into counts, and reject forged under/over selections before writing. A positive minimum rejects missing values; a maximum permits omission. Conditional limits stay in the active validation branch and their endpoint/model fields remain optional. Later visual edits preserve existing backend/routing snapshots and require explicit review; reconnecting does not silently migrate rules. The expanded `npm run test:checkbox-export` verifies authoring through an actual downloaded production Next/Express/MongoDB application locally. Multi-select count controls, compound conditions, mixed/nested composites and wider accessibility acceptance remain open.

## Conditional form sections

Form Field, Radio Group and Checkbox Group Content can show a section when an enabled, unconditional native Checkbox or Switch outside it in the same form is checked or unchecked. The condition stores the controller's stable element ID. Sections remain visible for editing. Preview and generated HTML/React use native hidden/disabled fieldsets, preserve entered values when toggled, omit hidden controls from submissions and restore authored defaults on reset. Initial generated markup applies the authored checkbox state before hydration; hidden Required fields cannot block submission. Authored disabling remains authoritative.

New guided collections snapshot each conditional field into ordinary If/Else and Validation blocks. The controller maps to a required Boolean body field, allowing literal false without imposing consent. Conditional request/model fields are optional; their active branches enforce authored Required and existing type/choice/text/date/file constraints. Inactive branches use the editable Must be omitted rule to reject supplied hidden values, including empty arrays and false, before storage. Existing Mongoose optional-array defaults remain unchanged. No hidden backend engine or automatic schema migration is introduced.

Existing endpoints require optional body mappings for conditional fields and a required Boolean body mapping for the controller. Their backend must explicitly enforce matching active/inactive branches; connecting or changing a visual condition does not rewrite existing workflow rules. Later edits preserve routing and backend snapshots and require review. Save/export rejects missing, disabled, conditional, descendant or cross-form controllers, nested conditional sections, split same-name radio choices and unsupported submit/custom/repeater/nested-form children. Whole-form copies and reusable form instances remap controller references; locked/linked sections require unlocking/detaching to edit their condition.

This accepts one checkbox predicate per native section outside repeaters and live record templates. Compound conditions, select/radio predicates, conditional chains, nested/mixed composites and catalog-wide accessibility/touch acceptance remain. Invalid arrays, duplicate/unknown/disabled values and boolean consent errors are rejected by the generated backend. Later edits preserve backend/routing snapshots and require explicit rule review.

This accepts direct checkbox groups, with the bounded section predicates described above. Compound conditions, minimum/maximum selection counts, nested/mixed composites, component structure overrides and catalog-wide screen-reader/touch acceptance remain open. ## Current architecture

UI elements retain stable IDs and native form/button behavior. Backend services and endpoint blocks retain their IDs. Routing connections bind these identities and resolve to ordered API calls and success navigation. Application generator version `semantic-2` now includes a contract index alongside the original project, graph, backend IR and definition metadata. AI design, patch and source requests receive this complete IR, after existing secret redaction and request-size checks.

A request field has an optional stable `id`; legacy fields use their original name until edited. The inspector preserves that identity on rename, and new inspector-created fields get UUIDs. Identities are scoped by endpoint and request location. Frontend implementation names do not have to match backend names. Schema validation rejects duplicate names/identities and reserved object keys. No eager migration rewrites old documents.

## Connect a form

1. Add a Form, its inputs, and a button with type Submit.
2. Connect the form output to an endpoint input on Routes.
3. Select the wire and choose **Map fields by identity**.
4. Assign each required body, query and path field to a form input or constant. A later endpoint may read a declared field from the previous response.
5. Connect the endpoint output to a page for success navigation, or another endpoint for an awaited follow-up call.
6. Optionally map declared response fields to text, title or paragraph elements, and configure the wire's failure message/navigation.

A submit button invokes its owning form. A legacy routing wire placed on a submit button resolves to that form. Wiring both creates a diagnostic rather than competing requests. Explicit click actions that prevent submission are reported. Separate buttons with type Button keep independent click behavior. Enter submission works through the same form handler.

Explicit mappings submit only mapped fields, read controls by element ID, convert scalar types, preserve unchecked booleans, and separate body/query/path data. Path segments are encoded. Unmapped required fields, deleted references, inputs from other forms, missing previous-response fields and invalid display targets are compiler errors. GET uses query/path fields. Bounded file inputs map to body objects using the submission attachment contract below; structured text-to-object conversion is not silently simulated.

Legacy wires without mappings retain name-based FormData behavior. Mappings and failure behavior participate in existing save/load and undo/redo. Deleting a mapped input leaves a diagnostic; it never silently falls back to guessing by name.

## Backend contracts

The endpoint inspector exposes body, query, path, request-header and response fields. Explicit query/path contracts validate and normalize scalar values on the server and discard undeclared values. Path contracts must cover each route placeholder; an explicitly declared string `id` supports slugs, while legacy CRUD paths retain MongoDB ID checks. Workflow responses with declared fields are checked before a login session is issued. Existing implicit lifecycle controllers retain their own response validation behavior.

Request Headers configure up to 32 application metadata fields with case-insensitive, hyphenated names and scalar types. Map them by stable identity in Routing using an input, literal or previous response. Required headers need explicit mappings; the legacy name-based form mode cannot supply them. Generated form requests keep headers separate from body/query/path data. Values are printable ASCII, bounded to 4 KB per field; the normal HTTP server's total-header limit also applies. Missing, malformed or repeated raw header fields are rejected before the endpoint executes. Header names with transport/browser/authentication duties are reserved; secret and identity credentials use existing server configuration and authentication paths.

Only declared headers enter workflows as `$request.headers`, with lowercase names and hyphens replaced by underscores (`X-App-Version` → `$request.headers.x_app_version`). Undeclared bindings fail compilation. The gateway forwards only the metadata declared by the matched endpoint; headers declared on another endpoint are not forwarded. Custom metadata does not establish a principal, tenant or granted capability. Built-in account forms retain their standard credential fields; lifecycle endpoints with additional required metadata need mapped canvas forms or a compatible client.

Response workflow blocks now expose **Response headers**. Add a name and a string, number or boolean literal, or a `$context.path` binding. The array persists in project IR and generated workflow JSON; names are case-insensitive and must be unique. Up to 32 application metadata headers are supported, with printable ASCII values of at most 4 KB and an aggregate 8 KB including names. Missing, structured, null, non-finite, oversized or control-character values fail before HTTP header writes and before login session issuance. Credential/secret bindings and browser, identity, cache, transport, correlation and security header names are rejected. Login headers share the existing restriction to earlier public outputs.

The gateway computes allowed response headers from the endpoint's reachable response blocks, including branches and nested operations. It forwards only those names, retains its private/no-store and cookie restrictions, and validates upstream values again. CORS Exposed headers must list any metadata a cross-origin browser should read; forwarding through the same-origin gateway does not make unexposed cross-origin headers readable. Error-handler responses do not inherit metadata from an unsuccessful workflow.

Explicit Response statuses 204, 205 and 304 send no body and ignore their value binding. A reachable 204/205 response conflicts with a nonempty endpoint Response Body contract and fails compilation. Express and the gateway preserve the status and headers for GET and HEAD; the generated API client returns null for successful 204/205 responses. Other error/status-specific response schemas, response-header Routing mappings, dynamic cache/security headers and nested response-body schemas remain open. Legacy inferred CRUD and built-in identity lifecycle controllers retain their existing output behavior.

Service CORS settings expose explicit HTTP(S) origins, allowed methods, automatic/custom allowed headers, exposed response headers, credentials and a preflight cache (0–86,400 seconds). Automatic allowed headers include Content-Type, Authorization and the service's declared endpoint metadata; a custom empty list allows none. An empty exposed list exposes no custom response headers. Runtime CORS_ORIGINS overrides are validated and normalized before identity origin checks. Wrong origins/methods/requested preflight headers fail closed; clients without an Origin header retain their existing server/API access and still require endpoint authorization. Wildcard/regex origins, per-endpoint/backend CORS scope and arbitrary transport/security header generation are not implemented. Health endpoints retain their separate public probe boundary. CORS does not replace authentication, same-origin protection or owner/tenant policies.

The generated frontend still uses the same-origin Levoks API gateway, declared endpoint allowlist, deployment-origin configuration, scoped cookies, and refresh behavior. Internal models and workflow blocks are not frontend destinations. Routing service-to-service edges chain endpoint requests in the triggering frontend flow; server-side upstream calls use the HTTP Request workflow block.

## Added executable capabilities

- **HTTP Request:** fixed upstream path, method, query/body bindings, origin environment variable, optional bearer-secret environment variable, timeout and GET retries. Supports JSON REST and GraphQL requests. The runtime rejects redirects, limits responses to 1 MB, and observes the existing workflow deadline. Errors enter the existing try/catch workflow. Mutation retries and HTTP calls inside retried database transactions are rejected.
- **Cache:** get/set/delete, namespace, key/value bindings and TTL. Entries are scoped by user and tenant and strip sensitive output fields. This is a process-local cache (256 entries, 64 KB each, TTL up to one hour), not a distributed or durable store. Transaction use is rejected.
- **Query pagination:** optional page binding, existing filtering/sorting/access policies, and existing per-page limit. Pages are bounded to 1–10,000; invalid values fail rather than causing unbounded reads.
- **Integration Service template:** endpoint → HTTP request → response, plus origin configuration.
- **Catalog Service template:** model and endpoint → filtered, sorted, paginated query → response.

Templates create normal blocks and connections; every block is editable/removable. Existing Auth, CRUD and Chat starters are retained. Chat remains an architecture starter, not a new WebSocket runtime. OAuth providers, general queues/jobs, file storage and arbitrary custom JavaScript execution are not added by this change.

## Guided form destinations

Select a Form → Content → **Submission destination**. **New submission collection** creates a local MongoDB service, a Submission model, a public POST `/api/submissions`, validation, a create query and a receipt response. **Create collection and connect** maps each enabled input by its element identity. Every generated block and wire remains editable in Backend and Routes. Each collection uses a distinct service/database fallback; setting multiple services to the same runtime database remains an explicit operator choice.

Alternatively, select an existing POST/PUT/PATCH endpoint and match its required body/query/path/header fields to form inputs. Names are suggested when they match; explicit mappings support differently named inputs. Existing constants are preserved and remain editable in Routes. Reapplying the same endpoint preserves response-display mappings and failure behavior. Arbitrary structured objects/arrays and chained response values require Routes. Passwords belong to identity workflows. Native radio groups, multiple selections and one bounded submission attachment are supported by the guided collection wizard; their detailed contracts appear below.

**Success message** and **Clear fields after a successful save** persist in the form. A failed request keeps entered values and prevents subsequent success actions. Successful requests display the authored message and optionally reset the native form. Disabled controls, including descendants of disabled fieldsets, are not submitted. The collection copies fields/validation when created; later model/contract changes are edited in Backend and mappings reapplied in the form panel. It does not silently migrate existing records when a form field changes.

Templates → **Add working contact form** adds an editable name/email form, database workflow and route in one undoable action, preserving existing canvas content. Disconnecting removes form routes while retaining backend blocks and stored records. Undoing configuration restores project definitions, not database contents from a running exported application.

The generated public endpoint returns only a receipt, with no submitted data or record ID. No GET/update/delete endpoint is created. For a connected MongoDB collection, Add private submission inbox now creates a separate identity service, operator permission/policy and authenticated read view; wider administrative account management remains open. Do not turn a public form into an anonymous read API. The default limiter permits 20 requests per 15 minutes per backend-observed IP, including invalid requests. It uses process-local counters, resets on restart, and visitors behind a gateway share its IP quota. Shared MongoDB counters are an existing Backend option; trusted proxy/client attribution and bot protection still require separate implementation/acceptance.

Generated frontend preview reports that no data was sent or saved: it does not run the backend. ## Submission attachments

The current larger/multiple attachment contract is described under [Point 4 authoring contracts](#point-4-authoring-contracts). The paragraphs below record the initial single-file increment; its 256 KiB ceiling is superseded.

Add native File Upload through Form → Content. Set an accessible label, field name, Required if needed, a maximum size in KiB (up to 256) and optional comma-separated filename extensions such as `.pdf,.txt`. Guided collection creation accepts one enabled file field with Multiple off. Invalid limits/extensions and multiple-file configurations fail visibly before backend/routing changes. Blank extension lists allow any valid filename; MIME patterns such as `image/*` are unsupported for this path. These checks inspect names, not file content.

The form reads the selected file asynchronously and sends exactly `{name, size, data}` as an object/body field, where data is canonical base64. Filename length is at most 120 characters with no path separators or control characters. Maximum decoded size is 256 KiB; exact decoded length must equal the declared integer size. Extra keys, malformed/noncanonical encodings, wrong extensions and oversized payloads are rejected. Shared generated browser/workflow/legacy validation enforces the same object contract. Required is a separate rule; optional missing selections are omitted. File selections are never serialized into project state or restored on reload. Successful native reset clears selection; failed reads/requests retain input.

The guided MongoDB model stores bytes atomically with the ordinary submission record. Existing request limits and public rate limiting remain. There is no separate blob upload, filesystem path or orphan cleanup to coordinate. New destinations snapshot an editable Submission attachment validation rule; later UI edits require reviewing its byte limit/extensions/message. Existing fields and records are not silently migrated.

Authenticated inboxes identify object fields with file validation rules and show Download filename (byte count), or Attachment unavailable for corrupt records. Downloads use a validated binary Blob with `application/octet-stream` and the submitted filename; the temporary browser URL is revoked. The existing live operator policy protects reads of both metadata and bytes. Attachment inboxes use five-record pages, enforced by the compiler; ordinary inboxes retain 50. Soft-delete, revoked roles, failed reads and sign out retain the existing private-record behavior. The table scrolls locally on compact screens and downloads remain keyboard reachable.

This completes bounded local submission attachments. General storage/upload/download blocks, cloud/CDN assets, larger or multiple attachments, MIME/content inspection, antivirus, authenticated visitor uploads, signed expiry, user quotas/retention and SQL/provider/container acceptance remain separate work. ## Private submission inbox

Account pages link to their connected inboxes after sign-in. Stale loads are aborted; loading, failures and sign-out clear rows. Focus/visibility changes reload access. Gateway and direct reads disable caching. Normal accounts, changed roles without grants, disabled users and revoked sessions are denied.

The separate identity account page offers **Set up first operator**. Setup codes are never generated into project data and Environment Variable blocks cannot hold them.

## Submission email alerts

After adding a private inbox to a connected MongoDB form, enable **Email alerts for new submissions** and edit its subject in Form → Content. Backend → Submission Email exposes the endpoint/create-query/model/inbox references. This is ordinary persisted configuration with undo/redo, not an executable workflow step. One configuration per non-relational MongoDB collection is supported; unsafe references or storage/credential changes block export.

The create query stores a hidden `_levoksSubmissionMail` job with the record in the same atomic write. No provider call occurs in the public API or editor preview. Validation/storage failures create no job. Disabling the configuration stops new jobs while previously queued alerts drain after deploying the configuration. Existing records do not acquire jobs retroactively. Neither public receipts nor private inbox responses expose the job.

The exported service adds `npm run worker:submissions` and `npm run notifications:status`. Copy `notifications/.env.example` to `notifications/.env`, set its database URL to the submission API's database, and configure the sender, single recipient, HTTPS frontend origin and provider key there or in the worker's environment. API `.env` and frontend settings do not need mail credentials. Compose offers an optional notifications worker profile with no public ports or JWT/setup tokens. Nested environment files are excluded from image build contexts. Read root NOTIFICATIONS.md for service names and setup.

Messages contain a generic notice and authenticated inbox link. Queue metadata stores subject/path snapshots and a salted fingerprint, not a recipient/key or submitted-data copy. Atomic leases and stable idempotency protect concurrent/restarted workers; changed mail settings after an attempted send fail safely. ## Native and nested form controls

Form → Content → Fields adds native text/email/number/phone/URL/date/time/datetime inputs, textarea, select, multiple select, checkbox, switch, radio button, Radio Group, File Upload and field groups. Choose **Add inside** to put a control in an existing group; **Edit** selects any native or legacy descendant, including disabled fields. Layers grips also accept native fieldsets as containers. Linked component children cannot change parent, and existing layers cannot enter linked component groups, until **Detach instance**. This uses ordinary undo/redo and does not implement structural instance overrides. Controls moved into a form's groups become normal-flow children at base and every saved responsive override; authored widths, content, identities and same-form request mappings survive. The shared semantic tree emits the same initial selection in HTML preview, React export and the canvas. Generic API array contracts retain their existing presence/type semantics. ## Choice and consent validation

New guided submission destinations create ordinary **Allowed values** (`oneOf`) rules for native Select/Multiple Select and enabled radio-group values. Single values must be listed; multiple selections must contain only unique listed strings. An optional empty selection is allowed, while required multiple selection retains its separate Required rule. Optional single-select placeholders are omitted from the request. Required checkbox/switch fields also receive **Must be checked** (`accepted`), which requires literal boolean `true`; sending `false`, a string or omitting consent cannot bypass validation. Optional booleans retain `false` as a valid value.

Backend → Validation exposes rule type, allowed values (one per line), other rule values, messages and removal with accessible labels. Invalid/duplicate choice lists show an inline error and cannot enter a valid saved project. Lists support 1–200 unique nonempty values with at most 10,000 characters total; radio values must fit on one line. Error Handler settings still govern public error messages.

Rules snapshot the fields when the destination is created. ## Date and time validation

Native Date, Time and DateTime fields expose minimum, maximum and step in Content. Date steps use days; time/local date-time steps use seconds. The backend inspector uses native pickers for bounds/initial value and a text interval control for positive numbers or `any`. Blank step uses the native default (one day or 60 seconds). Intervals below one millisecond are rejected. Invalid bounds, invalid initial values, inverted date/date-time ranges and invalid steps show inline errors; invalid configurations cannot compile/save as valid projects or create a collection. Time ranges may cross midnight.

New guided destinations snapshot an ordinary Date/Time/Local date and time Validation rule with `temporal` limits. The minimum anchors step; without a minimum the authored initial value anchors it, otherwise the epoch/midnight does. Calendar parsing rejects rollover dates, year zero, out-of-range months/days, leap seconds, timezone suffixes and wrong JSON types. Gregorian dates are bounded to the JavaScript Date arithmetic range with four–six digit positive years; times accept optional seconds and one–three fractional digits. Local date-time accepts the native `T` or space separator, with no timezone interpretation or conversion. Storage retains the submitted string. Browser/server behavior follows the [HTML input constraints](https://html.spec.whatwg.org/multipage/input.html#the-step-attribute) and [date/time string formats](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#dates-and-times), with the explicit interval/date bounds above.

Empty optional native temporal fields are omitted from mapped submissions; a temporal rule also allows an empty string for optional callers. Required remains a separate presence rule/endpoint contract. Disabled controls remain omitted. Existing destinations are not rewritten when form limits change: review their Validation blocks. Standalone workflow execution and legacy middleware use the same helper, preserving legacy PATCH behavior. Tests cover native Chromium/server agreement, actual authoring/error/undo/save/reload/preview/download, forged API values without writes, real MongoDB storage, outage/retry/reset and form bounds at 320/768/1024/1440px. Other browsers, screen readers and mobile picker interaction still need acceptance.

## Text formats, lengths and URL validation

Content exposes minimum/maximum lengths for native and legacy text-like inputs and Textarea. Lengths count UTF-16 code units, matching native controls (some emoji count as two). Authored lengths must be whole numbers from 0 to 10,000, with maximum at least minimum. Empty settings remain unset; zero is preserved. Imported noncanonical numeric strings, fractional/negative values and contradictory limits fail guided creation before any service is added. New guided destinations snapshot an ordinary **Text limits and format** rule. An unset guided maximum becomes 2,000 units (320 for email), raised to the minimum if larger. Standalone manually authored text rules cap an unset maximum at 10,000. Existing legacy Min/Max Length rules retain their behavior.

The native input Text format selector offers Any text, Numbers only (ASCII 0–9), Letters only (Unicode letters), Letters and numbers (Unicode letters/numbers) and Lowercase slug (ASCII segments separated by single hyphens). These fixed, linear patterns match the entire nonempty value and are shared by browser `pattern` and server text rules. Textarea uses length constraints and does not expose native input formats. Custom/imported patterns remain visible with a review-required state; guided storage rejects them and backend text-rule schemas cannot accept them. Arbitrary regular expressions/custom validation still require a separately reviewed workflow; this increment does not certify them.

URL inputs also snapshot an **Absolute URL** rule using the standard URL parser. The same check runs while serializing native form values in HTML preview and React exports, before any request. Special-scheme hostnames additionally reject forbidden domain characters, including percent escapes left in the parsed hostname by permissive browser parsers. This catches malformed hosts that Chromium's native URL field and parser accept, preserves input and shows a useful error. International domains, IPv6 and encoded paths remain accepted. Browser-native sanitization strips surrounding ASCII whitespace/newlines before serialization; direct API callers must omit surrounding ASCII whitespace and line breaks. This is syntax validation: addresses are stored without being fetched, and non-web schemes are not automatically permitted as rendered links. Existing safe-link rendering remains separate. See the [URL host rules](https://url.spec.whatwg.org/#forbidden-domain-code-point), [HTML URL state](https://html.spec.whatwg.org/multipage/input.html#url-state-(type=url)) and [native text length constraints](https://html.spec.whatwg.org/multipage/input.html#the-maxlength-and-minlength-attributes).

Empty optional text/URL/textarea fields are omitted from native submissions; the new rules permit blank optional strings from other callers. Required remains a separate rule/endpoint contract. Existing destinations and stored records are not rewritten after field edits. Backend rules expose editable lengths, format, message and inline errors through history/save/reload. Acceptance covers actual authoring/download parity, fixed-format/native comparisons, malformed URL rejection before POST, short and overlong forged submissions without writes, zero/emoji/optional semantics, rate limits, outage/retry/reset and four-width production form layout.

## Point 4 authoring contracts

These contracts supersede the earlier single-checkbox, direct-child composite and 256 KiB attachment descriptions. Existing saved projects remain compatible. A form destination snapshots validation into ordinary editable backend blocks; later visual edits require reviewing those blocks and mappings.

**Conditions.** Native Form Field, Radio Group and Checkbox Group can use an enabled same-form standalone Checkbox/Switch, Select/Multiple Select, Radio Group or Checkbox Group. Boolean sources compare checked/unchecked; scalar choices compare equal/not equal and arrays compare includes/excludes. A section supports up to eight predicates combined with All or Any, and a field can inherit up to sixteen conditional sections. Conditions inside an ancestor section may use its controls; sibling, descendant, cyclic and unavailable-choice references fail with repairable errors. Native hidden/disabled state preserves entries, omits inactive controls, updates dependent sections and restores defaults on reset. New destinations enforce every ancestor predicate, active requirements and hidden-field omission on the server, including literal choice values starting with `$`. Creating a destination that exceeds the 1,000-block workflow budget restores the entire project rather than adding an invalid service.

**Custom text formats.** The visual custom-format editor accepts bounded masks: `0` ASCII digit, `A` uppercase ASCII, `a` lowercase ASCII, `X` ASCII letter/digit, `L` Unicode letter/mark and `N` Unicode decimal digit. Other characters are literals; backslash escapes a token. Counts use `{n}` or `{n,m}` with an ordered 0–100 range and positive maximum. Masks have 1–120 characters; ambiguous adjacent variable repetitions and control characters are rejected. For example, `A{2}-0{4}` accepts `AB-1234`. Associated instructions, browser native pattern validation and copied server text rules share the same grammar. Arbitrary authored regular expressions and executable custom validation are outside this bounded contract.

**Attachments.** Up to five enabled File Upload controls can connect to guided submission storage. Per-file limits support 1 byte–1 MiB; the default remains 256 KiB. Multiple controls support a maximum of five files, minimum/maximum counts and a combined limit up to 1 MiB per control. Required has an effective minimum of one. A single field submits `{name,size,data}`; Multiple submits an array of those objects. Browser serialization checks counts/sizes before reading, then validates canonical base64, exact byte sizes, filenames and extensions. Generated APIs and gateways enforce a 2 MiB whole-request budget, including base64 overhead and other fields. Several large controls can exceed that budget; split the form or reduce limits. Bytes persist atomically with the record and the private inbox offers individual validated binary downloads. Extension checking is by filename; MIME/content scanning, general object storage, signed upload URLs, hosted assets, quotas/retention and provider acceptance belong to the remaining backend/infrastructure work.

**Nested and reusable editing.** A choice group can contain neutral Container/Stack/Columns wrappers and descriptive text, headings, images, icons or dividers; every nested choice keeps the group's name and one scalar/array field mapping. Other controls or separately conditional wrappers belong beside that group under Form Field. Existing Content/Layers moves preserve normal form flow. Linked instances can add, remove, move, reorder, group or ungroup children locally without detaching. A local structure override retains local nodes while following shared content/style changes; restoring shared structure preserves compatible content/style overrides. Publishing explicitly promotes the local tree. Clones and reusable instances remap conditions, choice names and standalone label associations; associated field IDs survive helper wrappers and save/reload.

**Geometry and responsive layout.** Drag/resize and vector handles map viewport coordinates through ancestor perspective, rotation, skew, scale, transform origins and canvas zoom. Resizing keeps the opposite projected corner anchored. Flow resizing uses relative offsets and retains the element's flow slot; root flow dragging uses reversible relative offsets. Normal form controls remain in flow during canvas selection. Grouping requires positioned siblings at every breakpoint; flow roots retain their existing structure. Group/ungroup preserves all saved breakpoint geometry; groups whose 3D/compositing transforms cannot be flattened safely retain their wrapper and explain why ungroup is unavailable. Collapsed projections have no editable plane. Transform authoring includes depth, X/Y/Z rotation, perspective (0 disables it), skew and scale. Motion composes with the base transform in both HTML preview and generated React applications.

**Custom breakpoints.** Up to twelve named widths from 240–20,000px extend Desktop, Tablet (1024px) and Mobile (600px). Widths are unique; 600/1024 are reserved. Overrides cascade from wider to narrower matching bounds. Content remains shared. Adding, renaming widths and removing breakpoints are undoable; width changes remap overrides in elements and reusable definitions, and removal clears the corresponding overrides. Inspector, canvas, saved project, preview and exported media queries use the same resolution.

**Flow and layout.** Labeled controls grow with labels and associated instructions; authored height becomes a minimum. Flow children are contained by their parent and eight section templates use growing layouts on small screens. Complete starter roots participate in exported page flow so long pages are reachable. Gallery columns/gap, repeater direction/gap, spacer height, menu direction and social-link size share canonical styles across canvas, HTML and React output.

**Structured content and widgets.** Rich Text supports bounded paragraph/heading/list/quote blocks with bold, italic, underline and safe links; visual text edits preserve unaffected spans. Timeline has editable, reorderable events with title/date/description. Both use validated JSON data and escaped semantic output. Maps validate latitude/longitude/zoom and generate an OpenStreetMap embed URL; actual remote-provider interaction remains point 6. Tooltips and popovers support placement, hover/focus as appropriate, Escape, nested dismissal and trigger focus return. Drawers use native modal focus management and four edge placements. Toasts support severity, dismissal, sticky duration 0 and bounded timed durations, pausing dismissal while hovered or focused. Native browser APIs are used rather than a separate widget dependency.

**Durable local history.** Project saves include a redacted, schema-validated local Undo/Redo journal, scoped to the account and written in the same conflict-checked transaction as the document. It stores at most 50 contiguous steps within a 10-million-character budget; stale/corrupt journals are discarded without discarding valid documents. Active typing/gestures can be autosaved with their undo baseline. Responsive editing batches retain the proper baseline. Source edits and project names participate alongside canvas/backend/routing state. Imported projects/checkpoint restoration clear unrelated history. Journals never enter downloaded applications or cloud/checkpoint documents.

**Complete starters.** Templates provides Studio (business), Maker (portfolio) and Workshop (registration) sites with local responsive previews of the actual editable tree. Each has working section navigation, a validated contact/registration form, ordinary submission model/workflow/routing and a private operator inbox. Applying a starter replaces the current page and adds storage in one undoable action; other pages remain. Preview submits no data until the starter is applied and Local full-stack or the exported app runs. The native preview dialog supports Escape, focus return and 320/768/1024/1280px review. No external template/demo site or paid service is required.
