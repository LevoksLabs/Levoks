# Managed frontend deployment

Updated 10 October 2026. This is the first managed-deployment increment. It deploys a Next.js frontend preview to an existing Vercel project. Express services, databases and generated email workers still require a separate host. Provider build readiness does not establish full application readiness.

## Full-stack container release — second increment

The application ZIP now includes a root `compose.yaml`, `deploy.mjs`, `DEPLOYMENT.md`, a configuration manifest and scoped runtime examples. Choose **Deploy → Download full-stack ZIP**. This runs the entire generated application on one existing Docker server; it does not provision that server or extend the Vercel adapter to host Express/database workers.

Configure the root `.env` from its example: a stable `COMPOSE_PROJECT_NAME`, public `APP_ORIGIN`, frontend port, required remote database URLs or local SQL passwords and, when used, one shared JWT signing secret. Configure each `deployment/<service>/api/.env` from its example. These service files use literal values through Compose's raw environment-file format; they are excluded from image builds and Git. The API receives its declared integrations, the database URL and appropriate identity configuration. JWT and operator setup tokens are absent from worker containers. Resend credentials are absent from API and frontend examples; provider files are passed only to their worker. Identity email encryption settings are shared between the API and worker through one runtime file.

Use Node.js 22+ and Compose 2.30+. Run `node deploy.mjs check`, then `node deploy.mjs up` in the extracted release. Optional `--identity-email` and `--notifications` flags require their profile-specific settings. The CLI checks required values, origin/port/signing-secret constraints, identity keyrings and local TLS incompatibility, pins the Compose file/project, and runs `config --quiet` before mutation. Docker failure output is replaced with a safe fixed message. `node deploy.mjs status` prints container state/health without environment values or raw logs. Profile flags select workers to start; omitting a previously enabled profile does not stop its existing worker. Stop that worker explicitly through Compose before disabling it.

Local MongoDB, PostgreSQL, MySQL, MariaDB and SQLite use retained named volumes. Backend/database ports are private. The frontend binds only to loopback for an operator-managed HTTPS reverse proxy. SQL initialization must complete before API startup; the existing schema fingerprint checks reject incompatible schemas and do not migrate application data. APIs must become healthy before frontend/worker startup. The generated dynamic `/__levoks/health` route checks every backend readiness route with bounded requests and returns only a generic ready/unavailable result. Selected workers publish process heartbeats checked by container health probes. Compose startup waits up to 180 seconds for health after builds. This gate proves readiness, not business behavior or actual email delivery.

The orchestration uses the documented [Compose health/startup dependencies](https://docs.docker.com/compose/how-tos/startup-order/), [raw environment files](https://docs.docker.com/reference/compose-file/services/#env_file) and [up/wait contract](https://docs.docker.com/reference/cli/docker/compose/up/). Local MongoDB remains private and unauthenticated, without TLS; use a managed remote database where that isolation is insufficient. SQLite supports one API replica. Stable project/service names retain storage; service renames and engine switches do not transfer data. Worker deactivation, traffic interruption during restart, schema migration, backup restoration and source archiving require operator handling. Automatic rollback, cloud provisioning, regions/resources/scaling, domains/TLS and zero-downtime rollout remain open.

Acceptance: five focused tests parse generated YAML for all database engines, storage/dependency rules, scoped secrets, profiles, collision handling, CLI validation/failure behavior and real HTTP readiness. A production standalone Next.js frontend runs against an actual generated SQLite API: create/read, same-origin denial, backend outage, restart and persisted data pass. A real generated worker process passes fresh-heartbeat, stale-heartbeat and stopped-process checks. The browser downloads and inspects the actual ZIP and its configuration guide. These are local runtime/contract checks; Docker execution and live providers remain unverified. Reproduce the native export checks with `npm run test:deployment-export`.

SQLite images include temporary Python/Make/C++ build tools during dependency installation, then remove them, so an unavailable native prebuilt addon can compile from source. This follows the [node-gyp Unix build requirements](https://github.com/nodejs/node-gyp#on-unix); the actual Alpine image build remains part of Docker acceptance.

## Public domain and HTTPS — third increment

The full-stack ZIP now includes `deployment/Caddyfile` and a Caddy 2.11.7 Alpine proxy under the optional `https` profile. With an existing server and a public domain, run `node deploy.mjs check --https`, then `node deploy.mjs up --https`. Add the same email-worker flags if required. Set `APP_ORIGIN=https://your-domain` with no custom port. The CLI derives the domain from this setting and overrides inherited or root-file `LEVOKS_DOMAIN` values. It rejects IPs, wildcards, malformed/local/reserved names, credentials and non-root paths before invoking Docker.

Point the domain's A/AAAA records at the server and allow inbound TCP 80/443; UDP 443 enables HTTP/3. Another process must not occupy these ports. Caddy forwards to the private frontend with its original host, uses automatic certificate issuance/renewal and HTTP-to-HTTPS redirection, and retains certificate/configuration state in named volumes. The API/database ports remain private; the existing frontend loopback port remains available for an existing proxy. Caddy's administrative API is disabled. Its container health probe measures its local listener, not public certificate validity.

After Compose health passes, `up --https` checks the public readiness endpoint using normal certificate validation and verifies the permanent HTTP redirect reaches the exact HTTPS readiness URL. Initial issuance gets six bounded attempts, at most about 85 seconds. Failed verification exits nonzero without deleting containers or storage. `node deploy.mjs verify` repeats this read-only check using only `APP_ORIGIN` in a root `.env`; Docker, the manifest and private API/provider files are not required. On another machine, copy just `deploy.mjs` and create an `.env` with that public origin, without database/signing/provider credentials. Run it there before release, since a check on the server cannot prove external firewall accessibility. The checker bounds responses, suppresses provider bodies and refuses `NODE_TLS_REJECT_UNAUTHORIZED=0`.

The verification establishes current public readiness; it does not identify a serving source revision or establish full application acceptance. DNS changes, wildcard DNS challenges, a domain administration UI, certificate status/renewal alerts and zero-downtime domain changes remain open. Omitted profile flags do not stop an already running proxy; stop its explicit Compose service before switching to a different proxy.

Acceptance includes generated YAML/domain/profile/CLI contracts and a native Caddy 2.11.7 process. The downloaded official binary was checked against its published SHA-512 checksum. The exact generated public-domain configuration passes Caddy adaptation/validation. Local real HTTP traffic preserves method, query, body, cookies and forwarding headers; a local Caddy certificate is rejected by the public checker as untrusted. The local CA stays in the test directory and OS trust installation is disabled. This is native provider implementation evidence, not live public DNS/ACME issuance, renewal or Docker evidence.

Reproduce the native proxy check after obtaining the official Caddy binary: set `LEVOKS_CADDY_BINARY` to its absolute path and run `npx tsx --test tests/integration/https-proxy.test.ts`. Without that variable the optional integration test explicitly skips. The browser ZIP test checks the proxy, public ports, configuration and verification guide. Sources: [Caddy automatic HTTPS](https://caddyserver.com/docs/automatic-https), [reverse proxy behavior](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy), [official Docker image](https://github.com/docker-library/docs/blob/master/caddy/README.md) and [published image version](https://github.com/docker-library/official-images/blob/master/library/caddy).

The official standalone Compose 2.30.3 binary also passes the generated CLI's actual version/configuration checks without a Docker daemon. Its download was checked against the published SHA-256 checksum. Frontend-only and complete five-engine/database/email releases validate with profiles disabled and all profiles enabled. Reproduce with `LEVOKS_COMPOSE_BINARY` set to the binary's absolute path and `npx tsx --test tests/integration/compose-release.test.ts`. These parser checks never invoke `up` or start containers. Both optional native checks are included in `test:deployment-export` when their binary variables are supplied.

Final increment evidence: 181 passing repository unit tests, 10 passing focused deployment/database tests, three passing native frontend/SQLite/worker/Caddy cases, one passing native Compose case, two passing deployment browser workflows and clean TypeScript/targeted ESLint. ## Archived release source — fourth increment

New managed previews persist the generated file map captured at queue time. The deployment worker reads that immutable archive and checks its source/configuration digest before marking submission. A compiler update or later canvas edit cannot silently replace queued source. Older jobs that predate archives still regenerate their saved project and must match their original digest. The archive is separate from the queue record so large source maps and 30 history entries do not exceed MongoDB's document limit.

In **Deploy → Managed frontend preview → Release history**, use **Download source** to get the exact captured files as a private ZIP. A ready release also offers **Requeue archived preview**, which queues a new preview from its archived source and saved API origins, independently of current canvas edits/checks. The connection must still identify the original Vercel project/team. The new release has a fresh operation ID and a reference to its source release. Interrupted requests retain that ID; matching concurrent retries create one queue entry. Only one release remains active at a time.

Source archives expire after 30 days and are removed when their release leaves the latest 30 summaries. Queue races can leave unreferenced archives, which are inaccessible through the download API and expire through the TTL index. Pruning is best effort with TTL as a fallback. Expired or corrupt source cannot be downloaded/requeued or newly submitted; an expired queued release fails before POST. Expiry does not cause an uncertain attempted submission to be reposted. Summary retention does not guarantee source remains available forever.

Archives contain validated generated text, after declared-secret redaction, plus the public API/app origin configuration and target identifiers. Provider authorization remains in the encrypted vault; runtime `.env` files and private keys are excluded by source-path validation. Arbitrary authored source/content is not secret-scanned. Archives are account-private compressed records in `levoks_deployment_archives`; configure database encryption/access/backups as appropriate. Source maps are limited to 1,000 files/10 MB, serialized archive input to 20 MB and compressed storage to 10.5 MB. ZIP responses and errors are private/no-store, and access requires the owning signed-in account and a matching retained history entry.

Downloading source does not restore a visual project document or include runtime credentials. Requeuing does not promote production aliases, roll back a backend, restore database contents or switch live traffic. Provider dependencies are rebuilt from archived source; resulting images/build outputs are not immutable artifact archives. Full-stack rollout/rollback and backup restoration remain open.

Acceptance: real MongoDB verifies source pinning, saved-config replay after canvas changes, reopening persisted stores, concurrent request identity, ownership, target mismatch, expiry, corruption before provider submission, 30-release pruning and legacy job integrity checks. A real isolated Next API with signed sessions verifies exact ZIP/compiler parity, private headers, guest/cross-account denial, same-origin replay protection and duplicate replay requests. Chromium verifies source download, interrupted requeue/retry, reload and 1600/1024px layout using controlled metadata. Evidence: `.verification/deployment-archives-mongo.log`, `deployment-archives-api.log` and `deployment-archives-browser.log`. These are local checks; live Vercel and container acceptance remain open.

API acceptance now uses a unique private build/config directory per run, allowing another development server to keep its deployment-test lock. Existing server processes and user data are preserved. The archive control layout was visually reviewed at desktop and compact widths; the Impeccable detector reports no findings.

Final fourth-increment checks: all 194 repository unit tests, two real-Mongo deployment cases, one real Next API case and two Chromium workflows pass. The production editor build includes `/api/deploy/archive` and passes private-output pruning. Sequential post-build TypeScript and targeted ESLint pass with zero findings; `git diff --check` passes. ## Configure

The editor and the separately supervised worker need `MONGODB_URI`, `LEVOKS_SECRET_KEYS` and `LEVOKS_ACTIVE_SECRET_KEY`. Use the same database and AES keyring on both processes. Retain old encryption keys while any records still use them. OAuth sign-in must be configured for the editor.

Run `npm run worker:deployment` with these variables in the process environment. The worker leases saved jobs, submits previews and polls the provider independently of the browser. It publishes a database heartbeat; the panel labels it offline after two minutes without a heartbeat. An offline worker leaves snapshots safely queued. Supervise and restart it as a separate service.

In **Deploy → Managed frontend preview**, enter the existing Vercel Next.js project's name and `prj_` identifier, optional `team_` identifier, and a scoped access token. Save the connection before queuing a release. Saving verifies project access/name/framework but does not create a deployment. The token is stored with authenticated encryption in a deployment-specific vault namespace, never returned by the API, and cleared from the input after saving. It is absent from project JSON, browser storage and exported code.

Enter an HTTPS origin for every authored backend service. Queuing validates the entire project and compiler diagnostics on the server, captures its current generated files/source overrides, and persists their archive. Before submission, the worker checks the captured source/configuration against the queued digest; legacy jobs regenerate their saved snapshot and require matching output. API origins are persisted with the connection; they contain no credentials. The worker uploads frontend files only, omits environment examples and injects a controlled `.env.production` containing these public origins. Backend credentials and hosting remain separate responsibilities. Only preview deployments are created; production aliases are not promoted.

## Releases, failures and recovery

Only one release can be active per account/project connection. Connection versions and queue sequences reject stale editors. The browser retries an interrupted queue request with the original operation ID and snapshot; identical concurrent retries create one job. Account changes and cross-origin mutations are rejected. Connection reads and responses explicitly disable caching.

The latest 30 release summaries are retained. Each records the operation ID, source/configuration digest, sequence, timestamps, provider ID/state and safe message. Completed jobs discard their queue snapshot; new source archives have the independent retention described above. A provider `READY` state enables the verified preview URL. `ERROR`, `BLOCKED` and `CANCELED` are terminal. A queued job may be canceled before a worker leases it. Canceling a provider build after submission uses the Vercel dashboard.

Before submitting, the worker durably records that a POST is about to occur. Concurrent workers use expiring, fenced MongoDB leases; expired workers cannot update release records. After a timeout, malformed acknowledgement or crash, a new worker searches up to five pages of provider history for the exact operation metadata and checks the returned deployment's project/operation before attaching it. It never automatically repeats an uncertain create request. Status failures use bounded backoff and stop after five attempts; **Resume status tracking** schedules another read/recovery attempt. Authorization can be replaced for the same target when no worker holds a lease, including while an uncertain release remains active.

An uncertain submission absent from the bounded provider search remains in **attention** and blocks another release. Review the provider project; automatic abandonment and duplicate submission are deliberately unavailable. This includes a crash between marking the submission and making the POST. Full operator reconciliation, disconnect/retention administration, immutable built artifacts and production/backend rollback remain future increments.

Provider error bodies and arbitrary build logs are never copied into release history. Logs are currently inspected in the provider dashboard; in-product log streaming/redaction is not implemented.
