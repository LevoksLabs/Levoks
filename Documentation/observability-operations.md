# Generated backend observability

The Health Check block under Observability configures a readiness route, database ping, required service liveness probes, per-probe timeout and result cache. These settings persist in project JSON and compile to `observability/health.js`. One block is allowed per service. Duplicate blocks, dangling/self dependency references, conflicting endpoint paths and attempted workflow use are compiler errors.

`GET /health/live` reports process liveness. `/health` and the configured readiness path return 200 only when every enabled probe succeeds; otherwise they return 503. The default is a MongoDB ping with a two-second deadline and one-second cache. During graceful shutdown readiness immediately changes to draining. Responses contain status and dependency IDs, without connection strings, provider bodies, cookies or tokens. Concurrent requests share a probe to bound load. Health routes bypass ordinary application rate limits and body parsing.

Set `HEALTH_ORIGIN_<canvas-port>` in the service runtime for each selected dependency. Origins must be HTTP(S) without credentials, paths or query strings. The generated Compose file uses service DNS names. Dependency probes check `/health/live`, avoiding recursive readiness chains; they do not prove the dependency's database or storage is healthy. Storage-specific probes and deployment rollout gates remain internal work.

Generated Dockerfiles run `observability/check.js` against readiness. The script exits nonzero for unhealthy services. Docker health status alone does not provide rollout or rollback orchestration. The generated script and HTTP probes are tested locally; Docker build/runtime verification requires Docker Desktop or an isolated Docker host, which is not available here.

Evidence: `tests/integration/health-runtime.test.ts` executes the emitted module with actual Express, MongoDB and HTTP dependencies, covering failure, timeout, concurrent probes, recovery and shutdown draining. The Chromium editor suite edits readiness settings in the inspector, reloads the workspace and inspects both emitted code and the ZIP's persisted IR.

Implementation follows [MongoDB ping semantics](https://www.mongodb.com/docs/manual/reference/command/ping/) and [Docker HEALTHCHECK behavior](https://docs.docker.com/reference/dockerfile/#healthcheck). Health Check remains PARTIAL until storage probes and deployed-container acceptance are complete.

## Error Handler and Audit Log

The Error Handler inspector configures a default client message, classified error logging and per-class HTTP status/message rules. Generated workflow and CRUD exceptions reach this handler. Duplicate database keys, validation failures, authentication/authorization errors, missing resources, unavailable dependencies and internal errors have defined classifications. Each request receives a fresh correlation ID. Logs contain classification, status, method and endpoint ID; raw exception stacks, driver messages, query strings and bodies are excluded. The Logger middleware uses the same metadata boundary for completed requests. Identity/validation handlers with explicit existing responses are not all routed through configurable classification yet.

Audit Log configures an event name, endpoint scope, read inclusion, actor/tenant ID retention, retention days, and whether requests must fail when audit storage is unavailable. The generated service creates its `levoks_audit` collection indexes at startup. Before executing a scoped request, it writes a durable start record with majority acknowledgement. Response completion or abort updates that record with the outcome and selected authenticated identity metadata. A TTL index expires records at their per-record expiry date. Audit indexes must be created successfully before the service starts accepting requests.

HTTP completion updates are separate from business mutations. A process crash or database failure can leave a durable `started` record with an unknown final HTTP outcome; the implementation does not infer success from it. The inspector's transaction-event option additionally records `transaction_committed` events inside each workflow Transaction block using the same MongoDB session. Audit failure aborts that transaction, and business rollback removes its event. These transactions use snapshot reads, majority commit acknowledgement and a bounded commit time. Standalone CRUD operations are not automatically converted into transactions. Background-process events, HTTP completion reconciliation, tamper-evident archival, a privileged audit browsing UI and host log aggregation remain internal requirements. Local retention is not a backup or compliance certification.

`tests/integration/backend-runtime.test.ts` uses a real MongoDB replica set to verify atomic business/audit commit, absence of audit events after business rollback, and business rollback when the audit collection rejects the event. This establishes the Transaction-block guarantee, not arbitrary custom-source auditing.

`tests/integration/observability-runtime.test.ts` uses generated routes, actual JWT middleware and MongoDB to verify scoped durable records, actor/tenant metadata, expiry indexes, correlation IDs, duplicate-key classification, denied requests, excluded reads, secret-free logs, and rejection before mutation when required audit storage is unavailable. The Chromium editor suite edits all three observability inspectors and verifies persistence and emitted source in the downloaded ZIP. BE48, BE52 and BE54 remain PARTIAL with this execution evidence.
