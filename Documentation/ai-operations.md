# AI proposal controls and verification

The AI assistant defaults to incremental visual edits. Providers return a bounded list of `add`, `replace`, `remove` and `test` operations using JSON Pointer paths. The server accepts changes only under editor, backend, routing and project name. Project identity, executable source and declared secrets are protected. Operations apply to a copy; the entire result must pass project/graph validation and cannot introduce new compiler errors. Existing compiler errors remain visible and are not reclassified as fixed by an unrelated edit.

Review shows each affected field with before/after excerpts. Applying retains the existing checkpoint boundary. The review signature includes project ID, name, design state and edited source, so renames, project switching and intervening canvas/source edits invalidate an older proposal. The complete visual replacement and source-file modes remain available separately.

Input byte and output token limits are configurable per request. The server checks the complete project/instructions before contacting the provider, and sends the selected output cap to inference. Usage display shows provider-reported input/output/total tokens; missing usage stays unavailable. These controls do not establish a monetary or account-wide budget. Durable usage accounting, provider pricing, context selection and generated-source semantic analysis remain internal work.

Evidence: `tests/project-patch.test.ts` verifies atomic application, preconditions, coordinated graph edits, schema/compiler regression rejection, pointer/array/prototype protection and bounds. API contract tests verify validation, output handling and rejection before a paid request when context exceeds the input budget. The Chromium editor test uses explicitly controlled model output to exercise review, explicit apply, saved state and rejection after a later project rename. It exposed and fixed a stale-proposal signature that previously omitted project names.

Live inference is not verified. To enable that check, choose a model supporting structured JSON output and enter its provider key in the AI assistant. Credentials remain in tab memory. After authorization, verify a small real patch, reported usage, cancellation, malformed/truncated output, the review boundary and a stale-proposal rejection. Tests have not contacted a paid model. Streaming uses bounded server parsing and browser proposal fragments. Partial output is display-only, cancellation discards it, and a proposal becomes applicable only after complete parsing and validation. HTTP integration checks use controlled provider streams; real Chromium tests exercise cancellation, review, apply and persistence. Live provider inference is still unverified.
